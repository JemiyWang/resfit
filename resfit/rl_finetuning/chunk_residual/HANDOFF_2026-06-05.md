## 0. TL;DR(结论先行)

1. **stageON(stage-conditioned + staged + as0.05 + actor_lr 1e-6 + cl=1 queue)塌**,塌点同样 ~20k,
   之后在 0.02~0.22 高方差低位带震荡,后5点滑动均值钉死在 ~0.13,**无回升趋势**(跑到 140k 仍如此)。
   -> stage-conditioning **没能阻止晚期阶段被带崩**,只是让"崩在哪一阶段"看得更清。
2. **残差不是没长出来**:residual_norm 四阶段都从 0 爬到 ~0.14 饱和。所以"1e-6 太小、残差≈0"被证伪;
   问题是残差**长歪了**(往破坏基座方向)。
3. **伤害高度集中在 stage3**:stage0/1 stay-rate ~0.9-1.0(健康),stage2 ~0.55,stage3 只剩 ~0.2-0.3。
4. **bonus 无辜,刷奖假设作废**:读 `chunk_env_wrapper.py` 确认 staged bonus 走单调闩锁(`self._stage=max(...)`,
   注释"防刷分"),`staged_bonus = bonus*(end-start)`,start=已闩住的最高阶段 -> 边界横跳领不到奖。
   -> stage3 崩**不是 reward hacking,是纯 critic Q 高估**(critic 把破坏性残差估高,actor 钻空子)。
   佐证:stage2 的 Q≈0 反低于 stage1(1.6)/stage3(1.0),不符合单调 bonus 结构 = critic 估歪的指纹。
5. **下一发杠杆重排序**:critic 侧(降 critic_lr / 更保守 target)第一优先,直击根因;
   actor 侧 stage-budget 卡 stage3/4 第二(需先实现);bonus 侧 `--reward_shaping potential` 零成本可叠(只削放大器)。
6. **wandb 上报已补齐并真环境验证过**(22 键全上报)。原 trainer 完全没接 wandb,这是它和原版脚本的一个差异。

## 1.5 [本轮新发现] chunk_residual three-piece base 用了 last,偏离全项目 best 惯例

- **现象**:stageON(及之前所有 cl=1 three-piece chunk_residual 实验)的 `--base_wandb_id` 喂的是本地
  `bc_run_..._three-piece_act/policy_step_199999`(**最后一步**),而 `build_base_policy` 对本地目录是
  "指哪读哪",根本不看 `wt_type`。-> **base 用的是 last,不是 best。**
- **对照惯例**:原版 `residual_td3.py` 每个任务(boxcleanup/coffee/cansorting/drawer/threepiece/threading)的
  `base_policy` 全是 `wt_type="best"`,`BasePolicyConfig` 默认值也是 `"best"`。**全项目惯例 = best**。
  连 three-piece 自己的原版 config(`residual_td3.py:322`,`dexmg-threepiece-bc/7zklm69g`,注释"BC best step20000+")
  也是 best。只有 chunk_residual 这一路用本地 last 覆盖掉了。
- **为什么 best != last**:本 BC 训练的 "best" 按**仿真成功率**选(`train_bc_dexmg.py:706-920`,非 val-loss),
  three-piece 的 best 冻在 **step 20000**(`best_step_20000` 是最后一个 best 快照;`best/` 改写时间 = best_step_20000)。
  之后 18 万步成功率没再涨 -> last(199999)很可能**弱于** best。已知 last 当 base 的 env_steps=1 eval = **0.300**;
  best 的数未测(BC eval 成功率只在 wandb / trainer_state.pt)。
- **影响**:所有 three-piece chunk_residual 塌掉的实验都是从**偏弱 base**(且非惯例 base)起跑的。base 越弱
  -> 成功轨迹越少 -> staged 成功奖励越稀 -> 越容易把 critic 拖悲观。**下一发必须换 best**,baseline 也值得用 best 重做。
- **修正(下一发用)**:`--base_wandb_id /data2/RL/residual-offpolicy-rl/bc_run_2026-05-31_14-59-16_dexmg-two-arm-three-piece-assembly_act/best`
  (build_base_policy 自动补 `/policy`;= step20000 best)。或走 wandb:`--base_wandb_id dexmg-threepiece-bc/7zklm69g`
  (chunk_residual 的 build_base_policy 对 wandb id 默认 wt_type="best")。
  **副作用红利**:换 best 后下一发的 env_steps=1 eval 即 best 的纯基座成功率,直接和旧的 0.300 对照,不必另跑 eval。
- **注意 caveat**:best-by-success-rate 用的是严格 `>` 且 BC eval episode 数有限,best@20k 可能含噪声(撞了次高 eval);
  故"换 best"后仍以下一发 env_steps=1 的实测为准,若 best 没明显 > 0.300 再议。

## 2. 诊断:三联图 + reward 源码(本轮核心认知)

### 2.1 plot_stage_diag.py 三联图(`outputs_chunk/cl1_stageON_as0.05_lr1e6/stageON_stagediag.png`)
- **target_q per stage**:warmup 后 stage1 顶到 ~1.6 并稳住,stage0/3 ~1.0,stage2 ~0。= **Q 高估指纹**。
- **residual_norm per stage**:四阶段 0 -> ~0.14 饱和。残差长出来了,不是≈0。
- **eval success + stage stay-rate**:success 在 0.02~0.22 低位带;stage0~1.0 / stage1~0.9 健康,
  **stage3 ~0.2-0.3 最惨**(=之前 stage-purity 测的 stage3 回退 ~75%)。
- 第四格(best.pt 各 stage reach 柱状)空 —— 需对 best.pt 跑 `reeval_stage_reach.py` 生成
  `<log>_reach.json` sidecar 才填。

### 2.2 reward 源码确认(`chunk_env_wrapper.py`)——排除刷奖
- `staged_bonus(start,end,bonus)=bonus*max(0,end-start)`(line 18-20)。
- `self._stage=max(self._stage,s)` 单调闩锁,episode 内只增不减(line 151,注释"防刷分");
  autoreset 才归零(line 170)。
- `start_stage=self._stage`(line 141)= 已闩住的最高阶段;发奖 `shaping_reward(start_stage,max_in_chunk,...)`(line 164)。
- **推论:每个阶段里程碑本 episode 只发一次,退回再爬回 start 已闩高 -> bonus=bonus*(k-k)=0。刷奖不可能。**
- `shaping_reward` **已实现 potential(PBRS)模式**(line 23-39):`bonus*(gamma*Phi(s')-Phi(s))`,
  done 时 Phi(s')=0。切换只需 `--reward_shaping potential`,**无需写新代码**。

### 2.3 根因结论
bonus 干净 -> stage3 崩只能是 **critic 把 stage3 破坏性残差动作的 Q 估高了,actor 做 Q 上升梯度去钻它**。
注意 actor 不"追大 Q":Q 整体抬高的常数对动作梯度为 0;害人的是 Q 的**错误斜率**(高估误差)。
staged(additive)会撑大 Q 量级 -> 高估的绝对误差更大(放大器),但不是根因。
